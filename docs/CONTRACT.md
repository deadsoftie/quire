# Quire Core API Contract — v1 (frozen)

Frozen at the end of M1 (task 1.9), per QUIRE_SPEC.md Section 0, rule 4:

> The contract in Section 6 is frozen after M1. Changing it means changing
> two platforms. Propose changes explicitly.

**Tag:** `contract-v1`, on commit `f73e04e` ("CoreAPI contract" — task 1.8's
implementation).

## Extensions since the v1 freeze

Per the rule quoted above, changes are proposed explicitly rather than made
silently. So far:

- **Task 4.5** (package manager panel) added three methods —
  `listInstalledPackages()`, `installPackage(name)`, `removePackage(name)` —
  and their supporting types (`InstalledPackage`, `PackageSource`,
  `InstallPackageRequest`, `RemovePackageRequest`) to `CoreApi`. v1's
  `prefetchPackages`/`bundleStatus` had no method that returned package
  *names* or removed one, and the panel genuinely needs both; there was no
  way to build it inside the existing shape. Proposed and approved before
  implementation (not retrofitted after).
- **Task 4.6** (bundle version pinning) added one field —
  `OpenProjectResponse.bundleVersionNotice: string | null` — since nothing
  in v1's shape could carry a quiet, plain-English notice back to the UI at
  project-open time. `openProject`'s own method signature is unchanged
  (still `Promise<OpenProjectResponse>`), so unlike 4.5 this needed no
  further wiring in `packages/client`, `quire-sidecar`, or the Electron IPC
  bridge — only the underlying response shape widened. Proposed and
  approved before implementation.

This document doesn't repeat the contract itself (QUIRE_SPEC.md Section 6
is that, and duplicating it here would just create a second copy to drift
out of sync). It's a map to where the real, frozen definitions live, and a
record of the judgment calls and current implementation state a future
reader — building M2's UI, or the M5 Capacitor transport — needs before
building against this.

## Source of truth

The contract's request/response/event types exist in exactly one place,
written once, in Rust:

```
crates/quire-core/src/rpc/mod.rs
```

TypeScript bindings are *generated* from those exact types via `ts-rs`
(`#[ts(export)]`, run by `cargo test -p quire-core`) into:

```
packages/client/src/contract.ts
```

**Never hand-edit `contract.ts`.** It's regenerated output — the file
itself even says so at the top (`// This file was generated by ts-rs ...
Do not edit this file manually.`). If a type needs to change, change the
Rust struct/enum in `rpc/mod.rs` and re-run the tests; that's the only
place a real contract change originates from.

The `CoreApi` *interface* (method signatures, as opposed to the data
shapes flowing through them) is hand-written, in:

```
packages/client/src/CoreApi.ts
```

This one genuinely has to be hand-written — Rust has no directly
derivable equivalent, since `quire-sidecar`'s dispatch is string-keyed
JSON-RPC (`match req.method.as_str() { "openProject" => ..., ... }`), not
a Rust trait object. `CoreApi.ts`'s method signatures match Section 6
exactly, including *which* methods take a single request object versus
positional primitive arguments (e.g. `setRoot(projectId, uri)`, not
`setRoot(r: SetRootRequest)`) — only the wire protocol underneath uses
request objects uniformly for every method; the public interface doesn't.

`quire-core/src/rpc/handlers.rs` holds the actual logic behind every
method that has real logic. `quire-sidecar` is a thin dispatcher over it
(deserialize params into the typed request struct, call the handler,
serialize the result) — see that crate's `main.rs`. Per D6, this means a
future `quire-ffi` (M5, Capacitor) calls the *same* handler functions
through a different transport, not a reimplementation.

## What's real vs. stubbed today

Section 6 specifies the full v1 surface, including methods and event
variants for features that don't exist yet (M3's completion index, M4's
package bundle system). Per the 1.8 decision, those are still part of the
*frozen shape* — the wire contract doesn't change when those features
land later, only the handler behind it does — but they don't do real work
yet. Building against this today:

| Method / event | Status |
|---|---|
| `openProject`, `setRoot`, `closeProject` | Real. `openProject`'s `bundleVersionNotice` is also real (task 4.6, new field — see "Extensions since the v1 freeze" above): `crate::bundle::record_version_pin()` compares `.quire/project.json`'s pinned `bundleVersion` (sibling to the compile shadow dir at `.quire/build/`, so already excluded from the file watcher and file tree) against `crate::bundle::digest_hex()`'s current one, returns a plain-English notice on a real mismatch, and re-pins to the current version either way — so the same notice never repeats on the next open. `null` covers both "versions match" and "nothing was pinned yet" (first-ever open). Deliberately *not* also re-pinned on `writeFile` (the bundle can't change mid-process, and `WriteFileRequest` carries no project context to do so without another contract field) |
| `compile` | Real — mirrors the whole project's file graph into the shadow dir per call (1.1's `FileGraph`), honors dirty buffers per-file |
| `cancelCompile` | Real, but lives entirely in `packages/client` (transport layer), not `quire-core` — see below |
| `complete` | **Real for `\ref`/`\eqref`/`\autoref` label completion (3.1), `\cite{` citation completion (3.2), bare-command macro completion (3.3, `\newcommand`/`\def`/`\DeclareMathOperator`, arity-driven tabstops), `\input`/`\include`/`\includegraphics` file-path completion (3.4, filtered to `.tex` vs. `project::GRAPHIC_EXTENSIONS`), bare-command CTAN package completion (3.5, merged into the same response as 3.3's macros, ranked below them via `sortPriority`), and bare-command math symbol completion (3.8, `crate::index::symbols`, merged into that same response one tier below package commands — Section 9.4's "global fallback," never scoped by `\usepackage` since these are core LaTeX/amsmath)** — `quire-core`'s own index, see `crates/quire-core/src/index/`. No longer backed by an external LSP tool. Path candidates come from a filesystem walk of the project directory (symlink-safe, `SKIP_NAMES`-aware), not the compile-side `FileGraph` — that only knows about references already written, not files available to reference. `.bib` files are discovered via `\bibliography`/`\addbibresource` in `.tex` source (there's no `Bib` `FileKind` in the compile-side `FileGraph` either — bibliography files aren't mirrored into the compile shadow dir, a separate, pre-existing gap 3.2 doesn't touch, see below). | `prefetchPackages` | **Real (tasks 4.3–4.4).** Scans every `\usepackage`/`\RequirePackage`/`\documentclass` across the project (`crate::index::ProjectIndex`), diffs the resulting `{name}.sty`/`{name}.cls` candidates against bundle + cache (`crate::bundle::missing_from_cache` — checked with the network tier forced cache-only, so the diff step itself never fetches), then fetches whatever's missing in parallel (`std::thread::scope`, one thread per missing file). `failed` reports package/class names; `fetched` reports `FetchedPackage { name, bytes }` — `bytes` is the real downloaded size (read off the fetched handle, since nothing in Tectonic's bundle API exposes size ahead of a fetch), which is what the missing-package card (4.4) shows next to each install. Called two ways: right after `openProject` succeeds and awaited before the first `compile` call on every real (non-scratch) project open (4.3, keeps that first compile from stalling mid-flight on a serial fetch), and again on demand from the missing-package card's Install button and its offline auto-retry-on-reconnect (4.4) — both call sites reuse this one handler rather than growing a second install path |
| `bundleStatus` | **Real (task 4.5 finished what 4.2 started).** `version` is the actual active Tectonic bundle digest — `crate::bundle::resolve_bundle()` (task 4.2) is a real three-tier chain, curated `bundles/core/` (built by `cargo run -p quire-core --example build_core_bundle` from `bundles/manifest.json`) → Tectonic's own local disk cache → network, for whatever core doesn't carry; the reported digest is always core's own when `bundles/core/` exists, since that's what defines this compile's identity, not an amalgam with whatever the fallback tiers also happened to serve. See `bundles/README.md`. `offlinePackages` is `crate::bundle::core_packages().len() + cached_packages().len()`; `cacheBytes` is `crate::bundle::cache_size_bytes()` — every byte under the cache tier's own on-disk directory, not just the `.sty`/`.cls` subset `listInstalledPackages` shows |

| `CompileResponse.diagnostics` | **Real (task 3.10).** `crates/quire-core/src/diagnostics/` parses the engine's own log text (not just the single top-level error message) into structured `Diagnostic`s: a regex-based translation table (`diagnostics/rules.rs`, 27 codes — the 10 named in Section 9.5 plus 17 more, all verified against real Tectonic output, not guessed) covers both fatal `!`-errors (fed from `CompileError.log` on the failure path) and non-fatal warnings that still appear on a successful compile (overfull boxes, undefined citations/references, "rerun needed" — fed from `CompileOutput.log`, which `rerun.rs`'s `run_tex_pass` now always returns, not just on failure). `diagnostics/file_tracker.rs` walks the log's `(filename ...)` push/pop nesting to attribute each diagnostic to a real file `uri`, mapping the engine's fixed `texput.tex` input name back to the project's actual root document. Suppression is real too: overfull boxes under 5pt never surface, and "rerun needed" is only reported from the *last* tex pass's log, so it naturally disappears once a later rerun actually resolves it. Its missing-file pattern (`diagnostics/rules.rs`'s `MISSING_FILE_PATTERN`) matches across Tectonic's own hard-wrapped log lines (`\s+` between tokens, not literal spaces) — a long package/class name routinely pushes " not found" onto its own line |

| `CoreEvent::IndexUpdated`, `BundleFetch` | **Never emitted** — nothing to update/fetch yet (M3/M4) |
| `Diagnostic` | **Real**, populated by `CompileResponse.diagnostics` above. Inline gutter/hover UI over these is a separate task (3.11) — 2.5's Problems panel already renders this shape today |

## Things worth knowing before building against this

- **`ProjectId` is the project's root directory's absolute path, not an
  opaque session handle.** `quire-core` holds no server-side project
  registry — per 1.4, every compile is a fresh OS process, so nothing
  could persist session state across calls even if it tried to. Every
  handler that needs "the project" re-derives what it needs (re-running
  root detection is cheap) from that path directly. `DocUri` is likewise
  just an absolute file path on desktop.
- **`cancelCompile` has no handler in `quire-core` at all.**
  `quire-sidecar` is one blocking process per compile with no in-process
  handle or side channel to cancel through (Tectonic exposes none, and
  the process is busy synchronously compiling anyway) — cancellation is
  real because `packages/client`'s `StdioTransport` kills the OS process
  directly. (`complete` *did* stay backed by a separate GPL-3.0 LSP tool
  for the same D7 reason through M2, but has had a real `quire-core`
  handler since 3.1 — see the table above.)
- **Bibliography files are invisible to the compile pipeline's own
  `FileGraph`, only to the completion index.** 3.2 added `\bibliography`/
  `\addbibresource` resolution to `crate::index` for citation completion,
  but `crate::project::FileGraph`/`build_file_graph` (what `compile()`
  actually mirrors into the shadow dir) has no matching `.bib` extraction
  — `IncludeCommand` only covers `\input`/`\include`/`\includegraphics`/
  `\subfile`. Every `rerun.rs` test that exercises BibTeX pre-copies
  `refs.bib` into the build dir by hand precisely because nothing in the
  real `compile()` RPC path does it. Until this is fixed, a real project
  with a bibliography likely can't cite anything successfully through the
  actual app, despite 1.6's BibTeX-rerun logic being fully built and
  tested at the `rerun.rs` level. Discovered during 3.2, not fixed by it —
  in scope for whoever picks up the compile pipeline next.
- **A failed compile is a normal, structured result, never a thrown
  error.** `compile()` only rejects/errors when the *request* itself
  can't be serviced (e.g. `projectId` doesn't resolve to a real project);
  a LaTeX error is `status: "errors"` with a `Diagnostic`, not an
  exception.
- **`compileId` is minted by the client (`StdioTransport`), not the
  server.** `quire-core`'s handler mints its own id purely for internal
  uniqueness; the client relabels the response with its own id so
  `cancelCompile`/`compile-started` events have a real, known-upfront id
  to correlate against, rather than two silently-disagreeing ones.
- **SyncTeX (`forwardSync`/`inverseSync`) is absent, not stubbed.** It was
  built during M0, then cut from v1 scope entirely after M1 (see
  QUIRE_SPEC.md 9.2) — Section 6 as it stands today never mentions it, so
  there's nothing to stub.

## Changing the contract after this freeze

Don't, without raising it explicitly first (Section 0, rule 4 — this
applies to the person *and* to an agent working from this doc). If a
change is genuinely needed:

1. Change the type(s) in `crates/quire-core/src/rpc/mod.rs`.
2. Re-run `cargo test -p quire-core` to regenerate `contract.ts`.
3. Update `CoreApi.ts` if a method signature changed.
4. Update every handler and transport implementation the change touches.
5. Update QUIRE_SPEC.md Section 6 itself — it's the spec of record; this
   file and the generated code both derive from it, not the other way
   around.
